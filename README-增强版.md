# TGbot-D1 3.0.5 增强版说明

本文件说明 3.0.5 增强版的改动与部署差异。增强版源自 realadmin 对原作者 [moistrr/TGbot-D1](https://github.com/moistrr/TGbot-D1) 的 Fork 自用改版，现以 PR 形式回馈原仓库；原项目未附开源许可证，分发与授权事宜见原仓库 Issue #16 的咨询。

增强版文件：`TGbot-D1创新版本3.0.5-增强版.js`（基于原版 `TGbot-D1创新版本3.0.5.js` 修改，原版文件未改动）。

**部署请看专门为本增强版重写的教程：[部署教程-增强版.md](部署教程-增强版.md)（小白向）。** 原仓库自带的教程（3.0.0 教程与 PDF）是给原版用的，其 setWebhook 示例缺少 `secret_token` 与完整的 `allowed_updates`，照它部署增强版会导致功能缺失，请勿混用。

## 增强内容

以下按功能主题归类介绍，不再按加入的先后排列；条目标题后的版本号是该功能首次出现的版本。

### 验证与通行证

1. **Cloudflare Turnstile 人机验证**
   - 待验证访客点击验证按钮后打开 Worker 自带的验证页，完成 Turnstile 校验即通过；验证链接以 Webhook 密钥做 HMAC 签名、绑定访客 ID、10 分钟过期，并核对 siteverify 返回的 hostname（v1.4.0 起改为必须返回、且须命中允许域名列表，缺失直接拒绝）。
   - 验证方式在「网页管理台」里切换（见第 15 项）；自 v1.4.0 起，选了 Turnstile 又未配置密钥时不再自动回退静态问答：访客会看到「验证服务尚未配置完成」的提示，主管理员也会收到告警，须补齐密钥或改选其他验证方式；静态问答仍可由管理员显式选用。
   - 静态问答验证加了防穷举（v1.2.2）：连着答错 5 次会锁定 30 分钟，锁定期间发什么都没有回应，过后自动解锁——出厂默认答案很简单，靠这个防有人对着答案一直猜；自 v1.4.0 起，管理台在问答答案仍是出厂默认值时会标红提醒更换，内置指南也同步提示。
   - 验证链接的有效期、问答连错锁定次数与锁定时长都可在管理台「基础配置」里调整（v1.2.3）；调短验证链接有效期不会作废已经发出去的链接，按发出时的时长到期。
   - 验证链接同样绑定访客本人（v1.2.3）：确认时校验打开者的 Telegram 身份，必须本人在 Telegram 里点开，转发给别人或用浏览器打开都用不了；提示文案里的有效分钟数按管理台设置动态显示。
   - 新增可选环境变量：`TURNSTILE_SITE_KEY`、`TURNSTILE_SECRET_KEY`；可选 `PUBLIC_URL` 覆盖验证页域名推导。
   - 顺序点击验证（v1.3.0 新增）：验证方式新增第三档。机器人发一条 3×3 按钮盘消息，从 6 类 emoji（水果 / 动物 / 食物 / 车辆 / 球类 / 表情）中随机选一类、抽 4–5 个作目标，访客按正文给出的顺序在 60 秒内点完即通过；每点对一步，盘面会重新抽取同类干扰项并洗牌；点错整题重开，并与静态问答共用同一套答错计数与锁定。不用打开网页、不依赖 Turnstile 密钥。

2. **验证调试工具**（v1.0.2 新增）
   - 管理员私聊发送 `/testverify` 可生成测试模式的 Turnstile 验证链接：走完整校验流程但不写入任何访客记录，可反复自测验证是否配置正确。
   - 在访客话题里发送 `/reverify`，可把该访客重置为待验证状态（重新走一遍验证）。

3. **一次性通行证**（v1.2.0 新增）
   - 个别访客怎么也过不了人机验证时，主管理员可在网页访客列表里给待验证访客点「🎫 通行证」：机器人会私聊对方发一张 30 分钟有效的一次性通行证，对方在 Telegram 内点开确认即通过验证，之后发消息时话题与资料卡照常自动创建；
   - 通行证链接带签名、绑定访客并带一次性随机数：确认时校验打开者的 Telegram 身份，必须本人打开才有效，转发给别人无效；用过即作废，重新发放会让旧证立即失效；被封禁的访客需先解封才能发放；通行证不依赖 Turnstile 配置，没配验证密钥时也能用。
   - 网页访客列表里点「🎫 通行证」有明确反馈：按钮先显示「发送中…」，成功弹提示并即时刷新该行，失败会写明原因（对方已验证 / 已封禁 / 发送失败等）；已发证未使用的访客行上带「🎫 已发证 · 剩 N 分钟」徽标，按钮显示为「🎫 重新发放」，谁有过证、还剩多久一眼可见；对方用证通过后徽标自动消失。
   - 通行证有效期可在管理台「基础配置」里调整（1–1440 分钟，默认 30 分钟）；调短不影响已经发出的通行证（v1.2.3）。

4. **验证消息自动清理**（v1.2.0 新增）
   - 验证流程里的机器人消息（验证提示、通行证消息、「🎉 验证成功」与「您已通过验证」提示）都会记下消息 ID 并在使用完毕后自动删除，不再在访客对话里越攒越多：反复索要验证提示只保留最新一条；通过验证时立即清掉验证提示与未使用的通行证；成功提示在访客发出第一条消息、进入处理时就删去（第一条消息被屏蔽关键词、类型过滤或限流拦下也照删，成功转发后再兜底清理一次）；过期未用的通行证在该访客下次来发消息时清扫。删除都是尽力而为（消息已被对方删掉等情况静默跳过），D1 里只存消息编号、不存正文，编号随访客记录一同删除。
   - 清理范围扩围（v1.3.0）：通过验证时，机器人发出的欢迎消息与访客自己最近发送的那条 /start 也一并删掉，验证前后的流程消息在访客对话里基本不留痕（更早发送的 /start 不在追溯范围内）。
   - 回执登记加固（v1.3.0）：六条发放成功提示的路径（静态问答、顺序点击、Turnstile、通行证、资料卡与列表设信任）统一收口到同一段发放代码；提示编号登记失败会自动重试，多次失败则把刚发出的这条提示删掉，宁可不留回执，也不留下一条谁也删不掉的记录。

### 消息转发与同步

5. **引用转发保留（含部分引用）**（v1.0.2 新增）
    - 任一侧在回复时引用了某条消息，转发到对侧时会带上引用：被引用消息按配对关系换算到对侧的对应消息，访客看到的是引用着自己原话的回复，管理员在话题里看到的同理。
    - 在客户端框选一段文字的「部分引用」也会原样带过去（片段文字、位置与格式一并保留）；引用对不上或原消息已删除时自动降级（整条引用 → 普通消息），保证消息本身不丢。

6. **消息编辑原地同步（替代原版的对比通知）**
   - 任一侧编辑消息，对侧对应消息原地更新（文字 `editMessageText` 并保留原格式、说明/媒体 `editMessageCaption` / `editMessageMedia`，媒体文件本身被替换时也能同步）。
   - 注：Telegram 对 Bot API 的编辑按静默编辑处理，不显示原生「已编辑」角标——所有机器人如此，非本版缺陷。
   - 无对应关系或原地编辑失败时，自动回退原版的「原内容/新内容」对比通知，编辑不会丢失。
   - 原地编辑成功后补发一条 `✍🏼已编辑` 提示行，以回复形式关联到被改的消息，作为「已编辑」的替代标记（v1.3.0 起文案精简）；提示行挂一颗「系统提示」按钮——内联按钮只有机器人能挂到消息上，访客自己发的同文案消息带不了按钮，仿冒提示一眼可辨。
   - 同一条消息多次编辑时，先撤回上一条提示再发新的，每条消息只保留最新的一条提示。
   - 编辑提示可在管理台「基础配置」里按方向分别开关（v1.2.3 起可整体关，v1.3.0 拆细）：「访客编辑是否提醒我」与「我编辑是否提醒访客」两项独立控制，关掉的一侧会在下一次编辑时把旧提示清掉；此前用总开关关过的部署按旧设置继续生效。

7. **消息反应（表情回应）双向同步**
   - 访客对消息贴/取消反应，话题中的对应消息同步；管理员在话题中贴/取消，访客侧同步（显示为机器人名义的反应）。
   - 仅同步普通 emoji，自定义表情跳过；机器人自身反应不回环；只对部署本版之后转发的新消息有效。
   - 以群身份发言的匿名管理员贴的反应也能同步了；付费反应（⭐）只叠加在普通反应之上，不会把已同步的普通反应顶掉（v1.2.2）。
   - 反应同步可在管理台「基础配置」里整体关掉（v1.2.3）。

8. **/delete 连带删除私聊原消息**（v1.1.0 新增）
   - 在话题里回复某条转发消息发送 `/delete`，除删除话题侧消息并打墓碑外，现按消息配对连带删除访客私聊中的原消息；管理员回复的消息被 `/delete` 时，其发到访客私聊的副本同样删除。
   - 访客已自行删除的原消息视为已删、不额外提示；删除失败（如原消息超过 48 小时、机器人被拉黑）会在话题里留一行说明。
   - 说明：Telegram 原生删除（右键 / 长按删话题消息）不会通知机器人（Bot API 没有消息删除事件），无法自动同步，连带删除请通过 `/delete` 触发。

9. **话题服务消息静默忽略**（v1.0.2 新增）
    - 管理员在话题里关闭/重开/改名话题或置顶消息时，Telegram 会在话题里生成服务消息；原版会把这类消息误当作管理员回复去转发，被 Telegram 拒绝（the message can't be copied）后又在话题里误报「转发失败」。现已在话题回复入口静默忽略这类服务消息。
   - **特殊类型消息占位卡**（v1.4.0）：投票、位置、地点、游戏、发票、联系人名片等本体无法复制的消息，转发失败时在话题里落一张「📩 访客发来一条『类型』，机器人无法转发本体。」的占位卡（来源内容受保护时同理），并给访客一句提示（同一访客 10 分钟内只提示一次）；占位卡照常建消息配对，回复它能送达访客、/delete 可连带处理。

### 访客管理

10. **拉黑 / 解除拉黑提醒**（v1.0.1 新增）
   - 访客在私聊拉黑（停止）机器人时，其话题内即时出现提醒；解除拉黑同样提醒；D1 标记去重。上线前已被拉黑的访客，在管理员回复发送被拒时走同一标记兜底提醒。解除拉黑、发出 ✅ 提醒时，之前那条 🚫 提醒会一并被删掉，话题里只保留最新状态。
   - 拉黑 / 解封提醒可在管理台整体关掉，两句提醒文案可自定义；提醒关着时对方解封，话题里旧的 🚫 提醒仍会被一并清掉，不会留下与现状矛盾的旧提醒（v1.2.3）。
   - **管理群成员看门狗**（v1.4.0）：名单外账号（不是主管理员、协管员与机器人自身）进入管理群时，机器人会私聊告警全体主管理员——是谁、被谁拉入、经哪个邀请链接；成员变动经 chat_member 更新感知，离群后标记清除、再进群会再次告警。看门狗只负责事后发现，预防仍靠群设置（新成员不可见历史、仅管理员拉人），详见第 16 项指南「成员纪律」一节。

11. **管理员备注**（v1.0.2 新增）
    - 话题命令 `/note 内容` 给当前话题访客存一条仅管理员可见的备注（上限 500 字、支持多行），`/note` 查看当前备注，`/notedelete` 删除；备注内容可能以数字开头也不会被误认为访客 ID，命令本身不会转发给访客。
    - 备注显示在话题资料卡上，保存/删除后资料卡自动原地刷新；网页访客列表里可查看、编辑备注，搜索可按备注内容命中。访客表新增 `admin_note` 字段，部署新版时自动迁移。
   - 话题名改为「备注｜名字 (ID)」：备注非空时取其第一行非空内容（单独限长 40 字）放在话题名最前面，在话题群的侧边栏列表里直接可见；无备注时与原格式一致。
   - 在话题里用 `/note` 设置、`/notedelete` 删除，或在网页访客列表里修改备注，话题名都会立即同步；访客改名触发的资料卡自动刷新同样带着备注，不会把前缀冲掉。

12. **已验证访客超时清理**（v1.0.2 新增）
   - 配置项 `verified_ttl_days`（网页管理台可改，默认 0 = 关闭）：超过该天数无活跃的已验证/待验证访客会被自动清除（含其消息记录与话题映射；旧话题保留为无主存档，访客回来会新建话题）。管理员与协管员豁免，活跃自动续期。被设为「信任」的访客同样豁免本清理（见第 14 项）。
   - 温和版「改回待验证」（v1.2.3）：另有独立配置项 `reverify_ttl_days`（网页管理台基础配置可改，默认 0 = 关闭）：已验证访客无活跃超过该天数时只改回待验证，档案、备注与话题映射全部保留，对方回来重新验证后还在原话题里继续聊；改状态不动活跃时间，删档清理的计时照常，两者可叠加（一般温和版天数设得更小，先改回、后删档）。被封禁 / 静音 / 信任的访客与管理员同样豁免。

### 服务熔断

13. **服务熔断**（v1.1.0 新增，v1.2.0 增强）
   - 被消息轰炸时可一键暂停机器人：主管理员在私聊或任意话题里发 `/pause [分钟]`（不带数字默认 60，上限 10080），或用主菜单的「⏸ 服务熔断」按钮、网页管理台的「服务熔断」区；`/resume` 随时恢复，到期自动恢复并私聊通知主管理员。
   - 服务熔断回复：每位访客每轮暂停最多收到一条提醒（默认「请稍后再试」），语句可在网页管理台修改或关闭（管理台里选「关闭：完全静默」时，回复语句输入框会自动隐藏）；已被封禁的访客不会收到回复。
   - 熔断期间访客新发的每条消息（文字、图片、语音、贴纸、文件等）一到达就被机器人删除：消息发出去就消失，访客立刻知道服务还没恢复；被封禁访客的消息同样删除且不发任何回复。
   - 每位访客收到的「请稍后再试」会记下消息编号；恢复服务时（手动 `/resume` 或到期自动恢复）原地改写成「✅ 服务已恢复，可以正常发送消息了。」并清掉记录，访客一看便知可以正常发消息了。
   - 访客在熔断期间修改熔断前已送达的消息、或给旧消息点 / 取消表情反应，都会照常实时同步到话题副本（编辑原地生效并带 ✏️ 提示；找不到配对的老消息走原有的对比通知），两边聊天记录始终保持一致；这两类动作不触发「请稍后再试」，因为动作已经生效。
   - 服务熔断到期后，恢复是「惰性」的：没有后台定时器，到期后第一条消息到来时才一并解除暂停并私聊通知主管理员；如果一直没人发消息，收不到恢复通知是正常的，熔断其实已经结束、只是没通知。
   - 开启服务熔断的确认消息（私聊 / 话题 / 主菜单已暂停状态行与选时长子菜单）、网页管理台提示与新手指南页都会把这件事写在明处，不会让人误以为机器人卡住了。
   - 恢复服务时翻成的那句文案可在管理台「文案与呈现」里自定义（v1.2.3）。
   - 恢复翻牌加固（v1.2.3）：翻牌单次限量且异常隔离，单卡瞬时失败保留记录待续翻，不再永久丢失。
   - 翻牌完成条件收紧（v1.3.0）：熔断状态改为翻完才清——一次没翻完的提示卡保留记录，随后续到来的消息分批续翻，全部翻完才结束本轮熔断状态；手动恢复时若整批翻不动也不会提前收工，管理员会收到尚余数量的说明，不再出现恢复后仍有个别访客的提示卡停留在「请稍后再试」。

### 网页与菜单

14. **网页版访客列表与数据统计**（v1.0.2 新增）
   - 主菜单的网页按钮打开访客列表（签名链接、10 分钟有效、仅主管理员）：可搜索、按状态筛选、排序分页，并可对访客重置验证或删除记录（可选连带删除话题，并连访客与机器人私聊里的聊天副本一起清空）。
   - 列表改服务端分页（v1.4.0）：搜索、状态筛选与排序改由服务端按游标逐页返回，不再一次拉回全量名单；名单再大翻页也不重不漏，待验证访客的通行证状态改为一次批量读取，不再逐人查。

20. **安全审计加固**（v1.2.0 新增）
   - 经过一轮全面安全审计，修掉一批细节问题：删人、重置验证与超时自动清理时会连带作废未使用的通行证（记录与证消息一起清），被删的人无法再凭旧证回来；人机验证确认补上封禁检查，被封禁者拿着封禁前得到的验证链接也过不了，与通行证确认口径一致；
   - 通行证的作废与清扫、发证流程、服务熔断的到期通知与熔断回复都改成原子操作：同一瞬间多个动作撞在一起，也不会误删刚发的新证、不会重复发通知或回复；外部验证请求加了 10 秒超时，初始化出错不再向外显示内部细节。
   - v1.2.2 完成第四轮全面审计，集中修了一批问题：三页签名链接按用途分权——访客列表、网页管理台、新手引导的链接互不通用，只读性质的指南链接不再等于一张全权通行证；新增可选变量 `LINK_SECRET`，设置后链接改用它签名、与 Webhook 密钥彻底分开（不设则沿用原密钥，行为不变）；带 @ 后缀的命令只认本机器人，发给别的机器人的命令完全忽略。
   - 同轮修好一批自己打架的细节：整段对话清空的收尾只删开始时拍下快照里的配对，清空期间新到的消息不受影响；拉黑→立刻解除拉黑时提醒的先后竞态堵上了，删除访客、超时清理、解除拉黑时拉黑提醒的记账都会清干净；/clear 的确认改成原子占用，同一张确认点两次只执行一次，访客档案已删除时点旧确认也不会把人「复活」成一条空记录。

21. **抗刷屏与数据库整洁**（v1.2.0 新增）
   - 封禁全入口统一、屏蔽即删（v1.3.0）：话题命令 /ban、/unban、资料卡的屏蔽按钮、网页访客列表的屏蔽开关、屏蔽关键词触发的自动封禁，五路走同一套生效逻辑；封禁后访客再发来的私聊新消息会被当场删掉并丢弃（含 /start，不转发、不回复）；封禁时发一条「⚠️ 您已被管理员封禁，无法继续发送消息。」（重复封禁不重复发），解封时先清掉这条、再发「✅ 管理员已解除对您的封禁，现在可以继续发送消息。」，解封通知会在访客下一条新消息到来时自动清掉。资料卡上的「🔕 静音通知」按钮同时下线——它只是逐条静默投递，容易被误解成 Telegram 原生免打扰（存量已静音访客的静默投递与超时清理豁免保留不变）。
   - 待验证访客反复发消息时，验证提示 3 分钟内只发送一次，其余静默丢弃，避免刷屏放大 Telegram 调用与 D1 写入（已发提示里的链接 10 分钟内有效，不影响正常验证）；被封禁或未通过验证的访客发表情反应不再同步进话题；已验证访客转发加了限流（v1.2.2）：短时间连发大量消息时，超出部分会被丢弃并在话题里提醒一次，防止单个访客刷屏把整个 Cloudflare 账户的请求额度耗尽（同一账户下的其他 Worker 会一起受影响）；消息转发失败不再静默丢失（v1.2.2）：话题里会出现 ⚠️ 提醒，机器人失去群管理员权限时还会私聊通知主管理员；话题被手动关闭时机器人会先把话题重开再投递，不再误判成话题失效去重建；节流用的时间标记会在验证成功、删除访客、超时自动清理时一并删掉，不在数据库里留残余。机器人不保存任何文件与消息正文，消息配对与去重记录 90 天自动清扫。
   - 消息处理改「至少送达一次」（v1.4.0）：Webhook 改为处理完成才回执，处理失败回 500 由 Telegram 重新投递，不再出现「双方都以为发出去了、实际已经丢失」；更新去重改两阶段登记，同一更新连失败 3 次转入死信并私聊告警主管理员，不再无限重推；中继复制前先落配对意向行，重投递时已转发的消息不会重复投递（长操作如整段清空、熔断翻牌仍走后台续跑）；Telegram 限流（429）改为按其给出的等待时长分流——要求等得太久时不在请求里硬等、改走失败重推；转发限流的可调上限收紧为突发 100 条、每秒补充 20 条（默认值不变）。

## 与原版部署的差异

除原版教程的变量（`BOT_TOKEN`、`ADMIN_IDS`、`ADMIN_GROUP_ID`、`WEBHOOK_SECRET` 与 D1 绑定 `TG_BOT_DB`）外：

1. 如需 Turnstile 验证，再加 `TURNSTILE_SITE_KEY`、`TURNSTILE_SECRET_KEY` 两个变量（Turnstile 小部件的主机名填 Worker 域名）；不加这两个变量时 Turnstile 方式不可用，请在管理台改选静态问答或顺序点击（v1.4.0 起不再自动回退问答）。可选变量 `LINK_SECRET`（v1.2.2）：设置后三页签名链接改用它签名，与 `WEBHOOK_SECRET` 分开；不设则沿用 `WEBHOOK_SECRET`。设置或更换后，已发出的旧链接立即失效，重新发送 /start 换新菜单即可。
2. 注册 Webhook 时必须带上 `allowed_updates`，且务必包含 `secret_token`，例如：

   `https://api.telegram.org/bot<机器人令牌>/setWebhook?url=<Worker地址>/webhook&secret_token=<你的WEBHOOK_SECRET>&allowed_updates=["message","edited_message","callback_query","message_reaction","my_chat_member","chat_member"]`

   其中 `message_reaction` 是反应同步的前提，`edited_message` 是编辑同步的前提，`my_chat_member` 是拉黑提醒的前提，`chat_member` 是管理群成员看门狗的前提，缺哪类就少哪类功能；`url` 必须以 `/webhook` 结尾（v1.4.0 起根路径不再受理更新）。
3. 机器人需要群组管理员的「删除消息」权限（编辑提示的滚动撤回要用）；置顶、删除话题等权限同原版教程。

其余部署步骤（建 D1、建 Worker、粘贴代码、绑定变量）与原版教程完全一致。
